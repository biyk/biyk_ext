# agents.md — deepVoyager

AI-подсистема модуля `biyk_ext`: управление NPC в бою через нейросеть (LRT/LLM-агент).
На ход NPC собирает данные о поле боя, отправляет промпт на локальный сервер
`http://localhost:9999`, парсит ответ вида `move/…`, `target/…`, `use/…`, `message/…`
и исполняет действия на canvas.

## TL;DR для агента
- Вход: `index.js → init()`, вызывается лоадером `biyk_ext/main.mjs` (расширение включается галкой в настройках модуля, регистрация в `registry.js`).
- Без запущенного сервера `localhost:9999` ход NPC падает с ошибкой fetch — `getAction()` не обёрнут в try/catch.
- План развития — в `todo.md` (server, TDD-расчёт путей своим кодом, очковая система, playground, долгосрочное планирование).
- Запуск сервера: `server\run_server.bat` — окно консоли видно (port 9999, конфиг `server/.env`,
  пакеты — только в `.venv`; вручную: `.venv\Scripts\python.exe server.py`).
- Остановка: Ctrl+C в окне или снятие процесса, слушающего 9999. NORMAL stop окно закрывает само
  (`timeout /t 2`), `pause` остаётся только при коде выхода ≥ 1 — чтобы успеть прочитать трейс краха.
- Тесты сервера (TDD): из `server/` — `.venv\Scripts\python.exe -m pytest tests`; собственный расчёт хода — `planner/` (шаг 4: перебор целей/маршрутов, очки, лимит времени; шаг 5: многошаговый lookahead, симуляция раунда, штраф урона, CLI-playground), файл ≤200 строк.
- Обучение нейроагента хода (шаг 6): `server\arent` — самодостаточная папка. На машине с 4060: `arent\setup.bat` (venv + torch: CUDA/`--cpu`/`--lite`/`--offline`, с проверкой свободного места) → `arent\build_exe.bat` (`dist\arent\arent.exe`) → `arent\arent.bat gen|train|bench|play|info`. Перенос одним архивом — `arent\pack_4060.bat` (+ `START_HERE.bat`/`.txt` на корне zip). Данные (`arent/data`), чекпойнты (`arent/runs`) и зависимости (`arent/.venv`) живут внутри `arent/`; учитель разметки — `server/planner`, поэтому копируется весь `server/`.
- Разметка и игра читают один чекпойнт: `net.save` пишет JSON-формат, общий для torch- и pure-python-политик, поэтому модель с видеокарты играется там, где torch не установлен (и наоборот, обучение идёт без GPU бэкендом).
- Подбор глубины и таймеров — не «на глаз»: `.venv\Scripts\python.exe -m playground --rounds 1,2,3,4 --timers 2,3,5,8` печатает матрицу «арена × глубина × таймер» с латентностью и значением линии в общей шкале.
- Аварийный откат многошаговости: `lookahead.rounds = 1` в `points.json` возвращает ровно сегодняшнее одношаговое поведение.
- Все тактические числа (очки, дистанции, лимит) — в `server/points.json`; правка подхватывается на ходу, без перезапуска.
- Пересобрать оглавление: `Select-String -Path agents.md -Pattern '^#{1,3} '` и обновить диапазоны строк ниже.

## 1. Архитектура и поток выполнения

Хуки `updateCombat` и `combatRound` → `combatTurn()` (только для GM, троттлинг 5 с):

1. **Фильтры**: нет текущего боевого токена / мёртв (`hp == 0`) / не `npc` / игра на паузе — выход.
2. **Сбор данных** (`utils/combat.js`, `utils/help.js`, `utils/tokenInfo.js`):
   позиция, скорость (шаги = speed/5), статус по HP, языки, disposition;
   видимые участники боя (прямая LOS + «расшаривание» видимости союзниками в радиусе 30 футов);
   группировка friends/enemies/neutrals; доступные действия (equipped weapon/equipment, spell, consumable) и feat-эффекты;
   `movement` — «роза движений»: сколько шагов в 8 направлениях до препятствия.
3. **Запрос к ИИ** (`actions/api.js → getAction()`): промпт строится `buildPrompt()`
   (обычный NPC) или `buildPromptBoss()` (disposition === -2), POST на `:9999/ask`,
   ответ парсится регуляркой `/(move|use|target|message)\/([^\n]+)$/gm` в `[{action, conf}]`.
   Боевой ход первым идёт `:9999/plan` — там вместо LLM свой перебор (шаги 3–5):
   плоский перебор кандидатов, а при `lookahead.rounds > 1` поверх него многошаговый
   поиск (симуляция раундов с жадным ответом врагов); лучший greedy-план остаётся
   фолбэком, поэтому план никогда не хуже одношагового.
4. **Исполнение** с лимитами за ход: `move = speed/5`, `use = 1`, `bonus = 1`, `target = 1`.
5. **Ветвление по disposition**:
   - `-2` (босс/DM-персонаж): исполняется только `target`, затем GM видит сырой ответ
     нейросети в Dialog-окне — ход вручную.
   - иначе: actions исполняются по кругу; при провале `move()` («ИИ затупила») —
     авто-фолбэк: поиск «Рывок» в инвентаре, запрос маршрута на `:9999/path`
     (`api.sendRequest(src, token)` с полным снимком сцены) и пошаговое движение по нему.
     В конце — `game.combat.nextTurn()`.

## 3. Контракт данных и формат действий

**Объект `data` для промпта** (`index.js`, шаги 1–3):
`{ name, x, y, speed, step, baseMove, status, languages, disposition,
friends[], enemies[], neutrals[], availableActions[], availableFeats[], movement{} }`
— каждый токен: `{ id, name, disposition, x, y, weapon, ac, status }`;
каждое действие: `{ id, name, type, uses, maxUses, recharge, range, rangeAll, damage, description, … }`.

**Формат ответа LLM** (по строке на действие, комментарии с `//` игнорируются):
```
move/up|down|left|right|upleft|upright|downleft|downright
use/<itemId>            # совпадение по similarity > 0.87 (Левенштейн)
target/<token_id>
message/<язык>/<текст>
```

**Ответ `:9999/path`**: `{ path: [direction…] }` — последовательность направлений,
по которой токен идёт без размышлений LLM.

**Формат запроса на `/path`** (`api.getAllData()`):
`{ src, token, data: { scene: {id,name,width,height,gridSize}, npcs[], walls[] } }`,
где `npcs[]` — все токены с центром/размером/HP/disposition, `walls[]` — стены/двери/окна
с точками A/B и состояниями closed/locked, полями move/sight.

**Эндпоинт `/plan`** (шаги 3–4 плана): payload как у `/path` + необязательные
`speed` (футы за ход, по умолчанию 30) и `weapons` (массив вооружения из
`utils/help.js buildWeapons()`: `{id, name, damage, attackBonus, sureFt, doubtFt, ranged, properties}`;
`ranged` — дальнобойность (в JS: `actionType === 'rwak'`; на сервере при отсутствии поля
выводится как `doubtFt > sureFt`, поэтому старый клиент тоже получает правило «в упор»);
`properties` — коды свойств dnd5e (`thr` метательное, `rch` досягаемость, `fin`, `amm`, …),
в JS снимаются с `system.properties` (в 3.x это Set, в 2.x — объект `{код: true}`);
в массив попадают предметы, которыми можно атаковать как оружием, — `actionType`
`mwak`/`rwak` (оружие в руках и природное оружие NPC, оформленное как `feat`);
без оружия атака не планируется). Ответ `{"actions": [{action, conf}…]}` — форма совпадает
с parseResponse() для `/ask`, поэтому combatTurn() не требует правок JS.
Логика: три источника кандидатов (quin-маршруты StrategyEnumerator → полный BFS-перебор
достижимых за ход клеток BruteForceExplorer → случайные прогулки RandomExplorer), замена
только при `score > best`, поэтому победитель детерминирован; при превышении лимита
времени (`limits.planTimeLimitSec`) фиксируется лучший из уже рассмотренных. Из каждой
клетки подбирается лучшая атака: оружие и зона (уверенная / сомнительная — награды
`actions.attack.sure` и `actions.attack.doubt`) выбираются по максимуму очков,
поэтому «подойти ради уверенного удара» против «остаться и выстрелить сомнительно»
решает арифметика. Очки за сближение считаются вдоль прямой до ОПОРНОГО врага: цели
атаки (из `target`-действия), если атака в плане есть, иначе — до ближайшего
(`scoring.Scorer.breakdown` возвращает `ref_kind`/`ref_id`/`ref_name`/`weapon_name`).
Раньше прямая всегда мерилась до ближайшего, из-за чего подход к собственной цели не стоил
очков, пока рядом стоит кто-то другой, и «стоять и стрелять на пределе уверенной зоны»
было равно «подойти и ударить» (побеждал первый по порядку кандидат).
Выстрел дальнобойным оружием в упор (цель не дальше `rules.pointBlankFt` футов =
соседняя клетка, включая диагональ) считается сомнительным и даёт `actions.attack.doubt`
очков вместо `actions.attack.sure`, поэтому планомерное сближение «до упора» невыгодно.
Исключение — метательное оружие (свойство из `rules.thrownProperty`): бросок вплотную
идёт без помехи, оно бьёт уверенно и в упор, и на своей дистанции.
Вставать на клетку существа нельзя (последний шаг убирается).
Выстрел по дальней цели, когда кто-то стоит вплотную, — нормальное поведение: помеха
привязана к цели атаки, а не к наличию соседа.
Если врагов/ходов нет — `{"actions": []}`.

**Многошаговый выбор (шаг 5)**. В `npcs[]` появились необязательные поля симуляции —
`speed` (футы за ход), `damage` (строка кубика «1d8»), `reachFt` (досягаемость его атаки),
`hitChance` (вероятность попадания); старый клиент их не присылает, и сервер берёт дефолты
из `points.json` (`rules.defaultSpeedFt` / `unknownDamage` / `defaultEnemyReachFt` / `hitChance`),
поэтому контракт `/plan` не изменился. Значение линии = сумма по раундам: награды `Scorer`
за раунд минус `actions.damageTaken.points` × вероятность попадания за каждый факт удара
минус `actions.damageTaken.death`, если в симуляции hp героя стал ≤ 0. Слой 1 перебирается
как раньше (top-`lookahead.topK` кандидатов с разнообразием «цель + финальная клетка»),
вглубь герой ходит компактным набором (остаться + лучшие `lookahead.shallowK` одношаговых
клеток), иначе дерево `O(K^R)` не считается вообще; каждый враг отвечает одним жадным
ходом (подойти по `legal_steps`, ударить, если достает) — без декартова произведения их
вариантов. Глубина наращивается 2, 3, … пока укладываемся в `limits.planTimeLimitSec`;
не успели — целиком отбрасывается последний слой и остаётся результат предыдущей глубины
(гарантированный фолбэк — сегодняшний greedy). На отбор кандидатов первого слоя отдаётся
`SCREEN_SHARE` бюджета, но не больше `SCREEN_MAX_SEC` секунд (иначе бесконечный
`RandomExplorer` съел бы время дерева).
Глубина выбрана по замеру playground (5 арен × `--rounds 1,2,3,4` × таймеры 2/3/5/8 с):
глубина 3 досчитывается за 1.6–2.6 с и даёт весь прирост значения (`pillars_three`: −27.8 →
+27.3, `glass_cannon`: 33.3 → 33.7), глубина 4 стоит до 4.3 с без прироста. Поэтому в
поставляемом `points.json` `lookahead.rounds = 3`, а `limits.planTimeLimitSec` оставлен 5 —
это и потолок дерева, и неизменный бюджет одношагового фолбэка (`rounds = 1`).

**Наблюдение модели (`arent/spec.py`, схема v1)** — то, что улетает в сеть вместо текста
промпта: фиксированный вектор (`spec.dims()` → `state`) из `me` (hp/ac/toHit/cr/скорость),
`weapons[]`, `enemies[]` (топ-K по дистанции, с `hit_chance(его бонус, мой КД)`), `allies[]`,
`others[]` и патча сетки 11×11 вокруг токена, где `@` — сам, `A` — союзник, `E` — враг,
`T` — прочий, `#` — стена, `.` — пусто. Действие разложено на три списка слотов
(клетки / цели / оружие) с масками; разметка учителя — просто индексы в этих списках.
Схема зафиксирована числом `SCHEMA`: при её смене старые выборки и чекпойнты отвергаются.

**Коэффициенты (`server/points.json`)** — единственное место, где живут тактические числа:
`actions.move.pointsPerCell` (очки за клетку сближения), `actions.attack.sure`/`doubt`,
`actions.damageTaken.points` (штраф за сам факт полученного урона) и `actions.damageTaken.death`
(штраф за «смерть» героя в симуляции), `rules.feetPerCell` (сколько футов в клетке),
`rules.pointBlankFt` (помеха дальнобоя в упор), `rules.reachToleranceCells` (допуск
диагонали/края токена), `rules.defaultMeleeFt` (дальность, если в запросе нет `sureFt`),
`rules.thrownProperty`, `rules.hitChance` (попадание без данных по КД), `rules.unknownDamage`
(чем бьёт враг без поля `damage`), `rules.defaultSpeedFt`/`defaultEnemyReachFt` (ход и
досягаемость токена без них), `limits.planTimeLimitSec`, `lookahead.rounds`/`topK`/`shallowK`.
Ключи английские, `comment`-поля — текст для человека, загрузчик их не читает. Правка файла
подхватывается на следующем запросе (сверка `st_mtime_ns` + `st_size`) без перезапуска сервера;
путь переопределяется `POINTS_FILE` (относительно `server/`). Неизвестный ключ, не-число,
битый или пропавший файл не ломают запрос: значения остаются прежними (последние хорошие
либо `DEFAULTS` из `planner/points_spec.py`), а в консоль печатается строка `[points] …`
с замечанием. `points.json` намеренно отличается от `DEFAULTS`: в коде по умолчанию
`lookahead.rounds = 1` (все существующие тесты и фолбэк остаются на одношаговом
поведении), а поставляемый файл включает многошаговость (`rounds: 3`).

Логи: консоль (`[plan] итог: …`) плюс постоянный двойной журнал `server/logs/requests.jsonl`
(машиночитаемый) и `server/logs/requests.log` (читаемый) — полное «что пришло → что ответили».
Каждый обмен помечается коротким идентификатором события `#<8 hex>` (`uuid4().hex[:8]`):
он стоит во всех строках консоли этого запроса, в поле `event` записи jsonl и в заголовке
блока текстового лога (`=== [ts] POST /plan #a1b2c3d4 ===`). По строке из консоли достаточно
вытащить этот id и найти его в `server/logs/requests.jsonl` — там весь обмен целиком.
Строка `оружие:` подписывает каждый entry именем и id (`Праща JRgq…[1d4 + @mod,
30/120фт, дальноб]`, метки `дальноб`/`метат`), а `итог:` печатает `сближение A→B футов
(+N) к цели` (или `к ближайшему`, если атаки в плане нет) и `Оружие → «Имя токена» <id>` —
по одной строке видно, чем, в кого и с какого расстояния били (имена токенов в бою
повторяются, поэтому рядом всегда id). Когда включена многошаговость, к этому же
`итог:` дописывается отчёт дерева: `R1 +31/-0 → R2 +1/-0 = 32` — на каждый раунд свои
очки (`+`) и штраф полученного урона (`-`), в конце — значение линии целиком; оно же
несёт `details`, поэтому `server.py` не менялся. При `lookahead.rounds = 1` отчёта нет —
строка остаётся ровно сегодняшней.
Проверить решение по записанному обмену: `python biyk_ext/temp/replay_event.py <event id>`
(выбранный план + топ кандидатов с очками), `… replay_event.py scan` — пересчёт всех
плановых событий журнала по теперешним правилам (скипт в gitignore-`temp/`, не часть сервера).

## 5. Паттерны и особенности

- **Единый источник коэффициентов (`server/points.json` + `planner/points_spec.py`)**: все
  тактические числа читаются через `tuning()` (замороженный dataclass `Tuning`); спецификация
  (`SPEC`/`DEFAULTS`/`_build`/`describe`) живёт в `points_spec.py`, состояние загрузчика
  (путь, mtime, «пришпиленные» значения) — в `points.py`, который её реэкспортирует. Оба
  модуля ни от кого в `planner` не зависят, остальные зависят от них — цикла нет. Числа по
  умолчанию зашиты только в `SPEC`, в коде планировщика констант нет.
- **Итеративное углубление с greedy-фолбэком**: частичная глубина отбрасывается целиком
  (`_Timeout`), поэтому результат — всегда полностью посчитанный слой, а худший случай —
  ровно сегодняшний одношаговый перебор. `PlanResult.depth/nodes/report` показывают,
  насколько глубины хватило времени; `considered` остаётся числом кандидатов первого слоя.
- **Симуляция = пересобранный `BattleContext`**: отдельной модели боя нет — `sim.Simulation`
  хранит позиции/hp и на каждом узле пересобирает токены и `raw`, поэтому `Scorer`,
  `best_strike` и quin работают на симулированном состоянии без правок. Один
  `PathfindingService` на состояние (npc_rects пекутся в `__init__` quin), иначе дерево
  тонет в пересборке A*.
- **Жадный ответ врагов вместо ветвления**: каждый враг делает один наилучший ход
  (сначала удар, иначе шаг, строго уменьшающий дистанцию); полное ветвление врагов
  (`O(K^R)` только на них) не разворачивается — дерево остаётся посчитанным за отведённые
  секунды.
- **Общая шкала сравнения — `sim.rollout`**: и greedy, и многошаговый план гоняются
  симуляцией на одно и то же число раундов; playground сравнивает именно это значение,
  а не очки планировщика (иначе глубокий план хвалил бы сам себя).
- **Кубики сводятся к ожиданию (`planner/dice.py`)**: `expected_damage`/`unknown_damage_avg`
  — среднее кубика, мода `@mod` и `/2` не резолвятся (долг), неразбираемая строка — это
  `rules.unknownDamage`, а не ноль урона.
- **`tuning()` берут один раз на функцию/цикл** (`t = tuning()`), а не на каждое действие:
  перебор клеток — тысячи вызовов, каждый сверяет `os.stat` файла. В `explore.py` `t`
  передаётся в `best_strike`/`_candidate` параметром.
- **Тесты пинируют дефолты**: autouse-фикстура `pin_default_tuning` в `tests/conftest.py`
  вызывает `points.set_tuning(points.default_tuning())` на время теста — иначе вручную
  затюненный `points.json` сделал бы существующие тесты хрупкими.
- **Проверка коллизий — трёхуровневый fallback** (`move.js`, `tokenInfo.js`):
  `CONFIG.Canvas.polygonBackends.movement.testCollision` → `token.document.checkCollision` →
  `canvas.walls.checkCollision(Ray)`. Клетка считается занятой, если живой токен
  (hp > 0) пересекает bounding box — заходить нельзя, только обходить.
- **Троттлинг хода**: `COMBAT_TURN_THROTTLE = 5000` мс + `setTimeout(500)` в начале —
  защита от двойных срабатываний `updateCombat`/`combatRound`.
- **Disposition-гейты**: обычная группировка — друзья по равенству disposition;
  для `-2` друзья = disposition `-1` (ИИ-враги игроков). Для `use`-действия с «Рывок»
  лимит движения увеличивается на `baseMove`.
- **Инъекция приказа GM**: `localStorage.gmNotes` попадает в промпт блоком
  «ВАЖНО! ПРИКАЗ ОТ ГМ» — редактор кнопки в трекере боя (`messageBox.js`).
- **Опциональный debug-режим `move`**: `conf.debug === true` — лог расстояний
  до препятствия в пикселях по 8 направлениям (лучевое сканирование по 1 px).
- **Макрос-проверка пути**: `game.modules.get("biyk_ext").api.testPath()` —
  по 2 выбранным токенам (или токен+цель) ходит первым ко второму через `/path`.
- **Факторизованное действие модели = разрез планировщика** (`arent`): состояние — фиксированный
  вектор (`spec.dims()`, сейчас 472 числа), действие — три замаскированные головы над списками
  слотов (куда / в кого / чем). Маски приходят из тех же списков слотов, что и `slots.decode`,
  поэтому ответ сети физически не может быть нелегальным планом, а разметка учителя гарантированно
  лежит внутри пространства модели (`dataset.sample_one` дополнительно проверяет round-trip и
  выбрасывает пример, если три индекса не собирают план учителя обратно).
- **Чекпойнт обучения — JSON со списками списков** (`arent/net.py`): формат общий у torch- и
  pure-python-политик, поэтому `train` на 4060 и `play` на машине без torch читают один файл;
  `format`/`schema` в заголовке проверяются при загрузке (чекпойнт старой схемы отсекается, а не
  предсказывает мусор).
- **Узкое место обучения — генерация разметки, а не сеть**: greedy-учитель на живом снимке
  (8 токенов, quin-маршрут в каждую достижимую клетку) даёт ~0.2 примера/с против ~20 примеров/с
  на аренах playground; 40 эпохи на 101 примере — ~130 с чистым python. Поэтому `gen` пинит
  `lookahead.shallowK/topK` и `rounds=1` (иначе разметка съедала бы `planTimeLimitSec` каждого
  состояния), а `config.json` хранит эти дефолты в секции `gen`.

## 6. Известные проблемы / долг

- `getAction()` без try/catch: сервер не запущен → необработанная ошибка в хуке, ход зависает.
- Награды задаются только глобально: per-weapon / per-заклинание коэффициентов в
  `points.json` нет, всё общее для `actions.attack`.
- Шаг 5 (многошаговость) закрыт: `actions.damageTaken.points` применяется в симуляции —
  `−30` × вероятность попадания за каждый факт удара, плюс `actions.damageTaken.death`.
- Враги в дереве не ветвятся: один жадный ответ на юнита, без их КД и без ограничения
  числа атак за раунд (оружие у всех — «одна атака за раунд»); `rules.hitChance` — общая
  константа, если в запросе нет `hitChance` конкретного токена.
- Смерть врага в симуляции не награждается отдельно: ценность снимаемой угрозы видна
  только как «во следующих раундах он не бьёт» (`glass_cannon` даёт +0.4 именно так).
- Союзники не симулируются (их ход — предмет шага 6); герой в симуляции бьёт только
  выбранным в плане оружием, заклинания/бафы вне модели.
- В строках кубика `@mod` и `/2` не резолвятся (`1d4 + @mod` → 2.5, без модификатора) —
  долг `planner/dice.py`; урон NPC без поля `damage` считается как `rules.unknownDamage`.
- По замеру многошаговость пока выигрывает на «выборе цели» и «снятии угрозы»
  (`pillars_three`, `glass_cannon`); на `fork_two_melee`/`bruiser_death`/`corridor_archer`
  значение линии одинаково на любой глубине — там штраф урона одинаков уже в слое 1.
- Очки за сближение не ограничены: план может побросать соседнего врага и бежать 6 клеток
  к дальнему (подход к своей цели плюс 8–9 очков) — штраф урона (шаг 5) это смягчает,
  но «цену» дальнего погони стоит пересмотреть отдельно.
- Лимиты в `combatTurn` прощают двойной `limit.move--` (шаг фолбэка + итоги после `move`) —
  при доработке аккуратно пересчитать семантику «шаги».
- `use.js`: `throw` с последующим недостижимым `return false`; `item.use()` работает только
  если предмет выбран/валиден для быстрый бросков — для части заклинаний могут требоваться цели.
- Регулярка `parseResponse` требует `$` в конце строки → действия, вклеенные в markdown-блок
  или с пробелами в конце, теряются; LLM может выдать несуществующие ID (частично лечится `similarity`).
- `getAllData()` собирает ВСЕ токены (`if (!isPlayerControlled || 1)` — второе условие always-true).
- `utils/dm.js` пустой; `init()` не снимает хуки при выключении расширения (reload=true).
- Промпты дублируют ~90% текста между `buildPrompt`/`buildPromptBoss` — при переносе расчёта
  пути на свой сервер (todo шаг 3) большая часть «move-инструкций» станет ненужной.
- `arent/torch_net.py` проверялся на этом CPU (глобальный `py -3` ставит torch 2.5.1+cpu, но
  `cuda.is_available()=False`, `nvidia-smi` нет): тест паритета градиентов pure↔torch прошёл и
  нашёл два реальных бага (коэффициент value-loss в torch был ×2 сильнее pure; в `pure_net._slot_backward`
  градиент `headU` домножался на `head[r]` — исправлено). CUDA на GPU здесь НЕ проверяется —
  реальный замер `bench --epochs 5` делают на 4060 и возвращают `runs/bench/bench.json`.
- Выборка `arent/data/samples` пока с одного живого снимка (`arena1_live`) плюс 5 арен:
  разнообразие позиций растёт только через `--per-src`/`--rounds-max` или новые снимки в
  `data/payloads` (их кладёт `temp/js_arena.js`).
- Модель ещё не повторяет план учителя целиком: на 101 примере 40 эпох чистым python —
  val cell 0.94 / target 0.88 / weapon 0.81, но joint 0.63 (и только 16 отложенных примеров).
- `arent play` не подключён к `/plan`: сервер по-прежнему считает greedy-перебор, модель —
  отдельный контур до тех пор, пока её точность не сравнится с планировщиком.
