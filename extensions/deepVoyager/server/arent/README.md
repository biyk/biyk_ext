# arent — обучение нейроагента хода NPC

Папка полностью самообеспеченная: код, данные, настройки, venv и собранный exe лежат
здесь же. Её можно скопировать целиком на другую машину (там, где RTX 4060) и работать
только с ней.

## Перенос на машину с 4060

Копировать нужно **весь** `server/`, а не только `arent/`: учителем разметки работает
планировщик из `server/planner`, а состояния берутся из арен `server/playground`.

| что делать с путём | зачем |
|---|---|
| `planner/`, `playground/`, `libs/`, `arent/`, `app.py`, `config.json`, `points.json`, `tests/` | копировать целиком — без планировщика `gen` не размечает |
| `arent/data/payloads/*.json` | копировать: иначе живых состояний нет, остаются 5 символьных арен |
| `arent/data/samples/*.jsonl` | по желанию: готовая выборка позволяет учить сразу, без `gen` |
| `.venv/`, `arent/.venv/`, `arent/build/`, `arent/dist/` | **не** копировать: окружение и сборка привязаны к машине (и в собранном здесь exe нет torch) |
| `arent/runs/<имя>/model.json` | обратно с 4060 одним файлом ~1 МБ — формат общий, здесь он играется и без torch |

`setup.bat` нужен только ради torch/CUDA (и pyinstaller для exe): `gen` и `train` проверены
на чистом Python 3.11 вообще без сторонних пакетов. Устройство выбирает `config.json`
(`backend.device: "auto"` → CUDA, если torch с ней установлен), руками можно `--kind torch|pure`.
Через git выборка и чекпойнты не доедут — `data/samples` и `runs` в `.gitignore`.

```
1. server\arent\setup.bat        # создаёт server\arent\.venv и ставит torch (CUDA 12.1)
2. server\arent\build_exe.bat    # собирает server\arent\dist\arent\arent.exe (нужен только для exe)
3. server\arent\arent.bat info   # чем считаем, где данные, сколько весов
```

Режимы `setup.bat` (проверяет свободное место ПЕРЕД скачиванием и не начнёт, если его мало):
`--cpu` — torch без CUDA (~200 МБ качать, всё равно быстрее pure), `--lite` — без torch вовсе
(только pure-python), `--offline` — torch из `.whl` в `server\wheels` (качать не нужно). pip
зовётся с `--no-cache-dir --retries 5 --timeout 120`, а временные файлы пишутся в
`arent\.pip-tmp` рядом с собой, а не на `C:` — это лечит `No space left on device` при
прошлой установке CUDA-сборки.

Чтобы перенести всё на 4060 одним архивом: `server\arent\pack_4060.bat` (код + арены +
живые снимки + выборки + чекпойнты; `--lean` — только код). На целевой машине — двойной
клик `START_HERE.bat`, подробности в `START_HERE.txt`. В архив не попадают `.venv`, `build`,
`dist`, `logs`, `__pycache__`, `.env`.

После сборки `arent.bat` сам делегирует команды в `dist\arent\arent.exe`; пока exe нет,
он запускает `main.py` из `.venv`. Рабочий каталог — папка рядом с exe: туда ложатся
`data/`, `runs/` и `config.json`.

## Команды

```
arent gen --count 400 [--name bc] [--seed 7] [--arena corridor_archer] [--no-live] [--append]
arent train [--dataset bc] [--name latest] [--epochs 40] [--batch 64] [--lr 0.003]
            [--hidden 96] [--head 24] [--kind auto|torch|pure] [--device auto|cuda|cpu]
            [--warm bc1] [--val bc1] [--keep-best]
arent bench [--dataset bc] [--epochs 5] [--kinds pure torch] [--devices cpu cuda]
arent play [--model latest] [--arena corridor_archer | --payload файл.json] [--out результат.json]
arent info
```

`--dataset` принимает одно имя из `data/samples` или путь к `.jsonl`. `--warm` — продолжить
весы из чекпойнта (имя прогона в `runs/` или путь к `model.json`), а не начинать со случайных:
формы `hidden`/`head` обязаны совпадать, чекпойнт другого размера — ошибка. Без `--warm`
каждая обучка стартует с нуля. ОПТИМИЗАТОР при `--warm` НЕ восстанавливается: чекпойнт хранит
веса, конфиг, размерности и метрики, но не состояние оптимизатора (моментум/шаги Adam) —
довыучивание загружает прежние веса и продолжает с новым оптимизатором. `--home <папка>`
целиком переключает рабочий каталог с `data/` и `runs/`.

`--keep-best` пишет два чекпойнта: `model.json` (ПОСЛЕДНЯЯ эпоха) и `model_best.json` (ЛУЧШАЯ
по метрике `val.joint`, а без валидации — `train.joint`; выбор строго `>`, то есть самый ранний
пик). В `summary.json` — поля `best_metric`, `best_epoch`, `best_is_last`. `--val` — отдельная
выборка-валидация (например СТАРЫЙ датасет при дообучении), а `val_by` в history/summary
разбивает метрику по источникам (арена/src) — это контроль забывания старых сценариев.
`--device cuda|cpu|auto` кладёт сеть туда, куда надо (для pure всегда cpu).

`bench` замеряет одну и ту же короткую обучку на pure / torch+cpu / torch+cuda (если cuda есть)
и пишет `runs/<имя>/bench.json` c `fastest` — не предполагаем, что GPU быстрее, а меряем.
`gen --append` дописывает новые состояния в существующую выборку, пропуская уже размеченные
(дедуп по ключу состояния). Сервер `/plan` складывает реальные боевые состояния в
`data/payloads/captures/` (`capture.py`, выключается `ARENT_CAPTURE=0`) — `payload_files()`
подхватывает их при следующем `gen`.

`gen` прогоняет состояния (арены + снимки из `data/payloads`) через планировщик и пишет
размеченную выборку. `train` — behavior cloning трёх голов (клетка / цель / оружие) плюс
стоимость линии. `play` — один ход моделью в формате, который понимается `/plan`.

## Где что лежит

| путь | назначение |
|---|---|
| `config.json` | размеры сети, гиперпараметры, дефолты `gen`; аргументы CLI его перебивают |
| `points.json` (рядом с exe) | коэффициенты планировщика-учителя: `build_exe.bat` копирует `server/points.json`, exe читает его сам (`POINTS_FILE` переопределяет) |
| `data/payloads/*.json` | снимки живых сцен (их кладёт `biyk_ext/temp/js_arena.js` через CDP) |
| `data/payloads/captures/` | реальные боевые состояния с `/plan` (`capture.py`, дедуп + усечение до 200) |
| `data/samples/<имя>.jsonl` | выборка: одна строка = один пример; рядом `<имя>.jsonl.meta.json` |
| `runs/<имя>/model.json` | чекпойнт последней эпохи (JSON, формат общий для torch и pure) |
| `runs/<имя>/model_best.json` | чекпойнт лучшей эпохи при `--keep-best` (метрика — `val.joint`) |
| `runs/<имя>/history.json`, `summary.json` | метрики по эпохам (`sec`, `val_by`) и итог прогона |
| `runs/<имя>/bench.json` | результат `bench`: секунды на конфигурацию и `fastest` |
| `pack_4060.bat`, `pack/` | упаковка проекта в zip для 4060 + `START_HERE.bat`/`.txt` |
| `.venv/`, `build/`, `dist/`, `runs/`, `data/samples/` | окружение, сборка и всё, что перегенерируется — в git не попадают (`data/payloads` остаётся) |

## Что видит модель

Наблюдение — фиксированный вектор: `me / weapons / enemies / allies / others / grid`
(патч 11×11 вокруг токена, `A` — союзники, `E` враги, `T` прочие). Размерность
`spec.dims()` возвращает `arent info`. Действие — три замаскированные головы над списками
слотов, поэтому любой ответ сети декодируется в корректный план; маски не дают выбрать
недоступную клетку, цель или оружие.

## Без видеокарты

Если torch не установлен, обучение идёт pure-python бэкендом (`arent/pure_net.py`,
ручной backward + SGD-моментум): ~50 000 весов на сотне примеров — секунды на эпоху.
Чекпойнт от обоих бэкендов одинаковый, поэтому модель, обученная на 4060, играется где
угодно, включая машину без torch.

## Сколько это стоит

Замер на этой машине (без видеокарты, `--per-src 8`):

| этап | объём | время |
|---|---|---|
| `gen` | 101 пример (64 с живого снимка + 37 с арен) | 457 с (~0.22 примера/с) |
| `train` (pure, hidden 96 / head 24, 50 812 весов) | 40 эпох | 130 с |

Базовый прогон `bc1` (эта выборка, те же веса, что лежат в `runs/bc1`): val cell 0.94,
target 0.88, weapon 0.81, joint 0.63, value_mae 0.59 — считать план учителя целиком модель
пока не умеет, этого и ждём от большего числа примеров и эпох на 4060.

Дообучение того же набора (`--warm bc1`, 8 эпох против 8 с нуля):

| прогон | val cell | target | weapon | joint |
|---|---|---|---|---|
| 8 эпох с нуля | 0.562 | 0.938 | 0.812 | 0.50 |
| `bc1` — 40 эпох с нуля | 0.938 | 0.875 | 0.812 | 0.625 |
| 8 эпох `--warm bc1` | 0.938 | 0.938 | 0.875 | **0.75** |

Поэтому на 4060 выгодно не перевыучивать с нуля, а наращивать выборку и дообучать её же
модель: `train --dataset big --warm bc1 --name bc2 --epochs 30`.

Узкое место — разметка учителя (перебор quin-маршрутов на живом снимке с 8 токенами), а не
сеть: на аренах тот же `gen` идёт в ~100 раз быстрее. Поэтому большие выборки собирают
заранее (`--count` с запасом, `--per-src` крупнее), а обучают по ним сколько угодно раз.

Замер `bench` на этой машине (CPU, без CUDA; torch не проверялся на GPU — это делают на 4060):

| конфигурация | pure (8 эпох) | torch+cpu (8 эпох) |
|---|---|---|
| hidden 96 (50 812 весов) | 24.86 с | 3.88 с (~6×) |
| hidden 256 (153 412 весов) | 40.27 с за 2 эпохи | 0.67 с за 2 эпохи (~60× на эпоху) |

quality (`val.joint`) у pure и torch при этом совпадает. Вывод: даже без GPU torch на обычном
CPU в разы быстрее pure-python, а настоящий прирост от 4060 надо мерить `bench --epochs 5` на
самой 4060 (CUDA здесь недоступна: torch 2.5.1+cpu, `cuda.is_available()=False`).

## Проверка

```
cd server
.venv\Scripts\python.exe -m pytest tests\test_arent.py tests\test_arent_net.py -q
```

Тест паритета градиентов pure↔torch (`test_pure_and_torch_value_gradients_match`) пропустится
без torch. Чтобы он реально прогнал сравни — запускайте pytest интерпретатором с установленным
torch (здесь это глобальный `py -3`), либо `setup.bat --cpu`/`--cuda` и его `.venv`.
