> на что ориентироваться и где остановиться. Пути — от `extensions/deepVoyager/server/`.

## 0. Цель и критерий приёмки

Получить **одну последовательную политику**, которая этап за этапом осваивает конкретные
тактики и **сохраняет** уже приобретённые навыки. Не «универсальную модель сразу», а
устойчивый прирост проверяемых способностей.

Приёмка всей работы:

1. **Навык.** Для каждой включённой тактики `follow_rate` (доля срабатываний среди состояний,
   где она применима) измеряется на известном фиксированном наборе И на новых состояниях того
   же типа. Порог задаётся до прогона (§6).
2. **Боевой эффект без shaping.** Командный matchup против фиксированного соперника
   (Random и/или Greedy/Battlecast) с side-swap показывает измеримое улучшение урона/убийств/
   выживаемости/исхода там, где тактика реально влияет на результат.
3. **Отсутствие регресса.** Ранее сданные этапы не падают ниже заранее заданного допуска.
4. **Осмысленность против случайности.** Модель превосходит RandomPolicy там, где решение
   вообще существует. На зеркальных дуэлях равных составов проверяется **отсутствие преимущества
   стороны** (side-swap win≈loss), а НЕ потолок побед.

Красная линия: если PPO не осваивает простую дуэль (этап 1), весь curriculum на PPO
**не** запускается — сначала диагностика (§8).

## 2. Инвентарь данных и что детекторы могут видеть СЕЙЧАС

Перед тем как что-то обещать в тактиках — фиксируем, какие сигналы реально доступны после
шага среды (`sim.advance`/`apply_actor_seq` → `info`, `state.units`). Это границы честности
детекторов.

Доступно надёжно:
- `hp_before/after` по всем юнитам (`prev_units`, `state.units`), `Unit.is_alive`, `Unit.hp`.
- `cell` каждого юнита (row,col), `cell_distance`, `within_reach` (`geometry.py`).
- `striking_distance(ctx, a, b, reach, sight)` — досягаемость И линия видимости (`los.py`).
- `reach_cells`, `speed_steps`, `damage_avg`, `chance` — из `Unit` (`initiative.py`).
- выбранная цель/оружие/клетка действия — из `action` (slots.decode).
- исход шага команды — `TeamReward.step` (win/loss/draw/mutual, kills, hits).

Ограничения (не изобретаем):
- **Высоты/возвышения нет** → любой тег про high ground невозможен.
- **Opportunity attack нет** → угроза = «враг бьёт в `foes_act`, если ты закончил ход в его
  `striking_distance`». Всё «избежание reach» строим вокруг этого.
- **Укрытие бинарное** (LOS есть/нет). Градации «½/¾ покрытия» нет.
- **Точность героя** в `apply_actor` берётся из глобального `t.hit_chance` (0.65), а не из
  актёрского (помечено в коде как «долг»). Для `kill_shot` порог ожидаемого урона считаем по
  той же формуле, что и среда (`weapon.expected_damage * t.hit_chance`), иначе детектор
  разойдётся с реальностью.

Вывод: тактики, которым не хватает данных, **откладываем точечно**, остальной curriculum
продолжаем (требование 2.4).

## 3. Готовность тактик (вводим по этапам, не всё сразу)

Каждый тег описан шестью полями: применимость / нужные данные / успех / ошибка /
«нейтрально» (нельзя ни бонус, ни штраф) / юнит-тест позитив+негатив.

### 3.1 Готовы к реализации сейчас

**`no_idle`**
- Применимость: у актёра есть хотя бы одна легальная атака или полезное сближение (дистанция
  до ближайшего врага сократится либо войдёт в зону удара).
- Данные: legal-маска, `cell`, дистанции, `striking_distance`.
- Успех: в ходу есть атака ИЛИ перемещение, уменьшающее дистанцию до цели.
- Ошибка: ход без атаки и без сближения (стоит/крутится на месте), когда атака была доступна.
- Нейтрально: сближение физически невозможно (закрытый проход/ walls), атаки нет — не штрафовать.
- Тест: «стоит при доступном ударе» → − ; «бьёт/идёт» → + ; «тупик, ударов нет» → 0.

**`focus_wounded`**
- Применимость: ≥2 живых досягаемых врагов.
- Данные: `hp`, достижимость (`striking_distance` из плана хода), ожидаемый урон.
- Успех: цель = живой с **минимальным `hp_before − ожидаемый_урон_по_ней`** (добиваемый/раненый),
  а не просто мин.HP; учитываем достижимость.
- Ошибка: ударили полного/недостижимого, когда раненый достижим и добиваем.
- Нейтрально: все цели равны по добиваемости; цель недостижима — 0.
- Тест: раненый достижим vs полный недостижим → + за раненого; оба недостижимы → 0.

**`kill_shot`**
- Применимость: есть цель, у которой `hp ≤ ожидаемый_урон(герой→цель)` (та же формула, что среда).
- Успех: выбранная цель = добиваемая (одна из).
- Ошибка: есть добиваемая досягаемая, а бьём другую.
- Нейтрально: добиваемых нет; добиваемая недостижима — 0.
- Тест: hp 6, our exp dmg 8 → обязан взять её; exp dmg 3 < 6 → не требовать kill_shot.

**`priority_soft`**
- Применимость: ≥1 живой ranged/reach-угрозы **и** melee-цель, все досягаемы в этом же ходу.
- Успех: ударили ranged/reach (мягкую угрозу) раньше танка.
- Ошибка: бьём танка/melee, пока мягкая угроза жива и досягаема и стреляет по нам.
- Нейтрально: мягкие недостижимы/мертвы; только melee → 0.
- Тест: archer+tank в радиусе, взят archer → +; archer за стеной (нет LOS) → 0.

**`focus_fire`** (команда/раунд, не одно действие)
- Применимость: ≥2 союзника сделали атаку в раунде, ≥2 врага живы.
- Данные: атаки всех актёров команды за раунд (`polyenv`), hp-дельты целей.
- Успех: ≥2 союзнические атаки пошли по **одной** цели, которая умерла или получила max урон.
- Ошибка: атаки размазаны по разным целям и никто не умер.
- Нейтрально: только 1 атака за раунд; целей нет (1 враг) → 0.
- Тест: 2 атаки по F1 (умер) → + (один раз за раунд); 1 по F1,1 по F2, оба живы → −.

**`break_ring`**
- Применимость: актёр в «контакте» с ≥2 врагами (2+ врага в своей `striking_distance`).
- Успех: за ход число контактных врагов стало ≤1.
- Ошибка: за 2 хода контактов стало ≥3.
- Нейтрально: не было выбора (все выходы под ударами) — считать по `foes_act`-урону.
- Тест: из 2 контактов вышел в 1 → +; вошёл в 3 → −; замкнутый коридор без выхода → 0.

**`kite_max_range`** (переопределён честно)
- Применимость: у актёра ranged-оружие (`doubt_cells` ≥ 30) и есть живой милишник-угроза.
- Данные: `striking_distance` милишника до актёра, возможность актёра дострелить после хода.
- Успех: после хода актёр **вне** `striking_distance` ближайшего милишника **И** сам достаёт цель.
- Ошибка: закончил ход внутри зоны милишника (получит урон в `foes_act`) либо потерял выстрел.
- Нейтрально: нет милишников; уцелеть-и-выстрелить физически несовместимо (тупик) → 0.
- Тест: вышел на 2 клетки от melee и стреляет → +; встал вплотную → −; только лучники → 0.

**`avoid_reach`** (переопределён: не про AoO, а про финальную клетку)
- Применимость: на поле есть враг с `reach_cells ≥ 2` (10 ft) — пики/дальнобой как угроза.
- Успех: ход, после которого актёр **не** внутри `striking_distance` такого врага, если мог.
- Ошибка: закончил в зоне reach-врага и `foes_act` задел актёра.
- Нейтрально: иначе не добраться до цели; reach-враг мёртв → 0.
- Тест: вошёл в 10ft к пике, получил урон → −; обошёл → +; выхода нет → 0.

**`cover_shoot`** (переопределён: бинарная LOS относительно цели)
- Применимость: актёр стреляет, и в геометрии есть стена `sight>0`.
- Успех: после выстрела прямая «актёр→цель» перечёркнута (нет `has_los`), т.е. встал закрыто.
- Ошибка: после выстрела остаётся на открытой LOS к цели/стреляющему врагу.
- Нейтрально: стен нет вообще; выстрел только из открытой позиции → 0.
- Тест: выглянул-выстрелил-ушёл за стену → +; стоит на LOS → −; аренa `open` без стен → 0.

**`anti_pincer`**
- Применимость: актёр зажат с ≥2 направлений (враги с разных сторон в `striking_distance`).
- Успех: атаковал **ближайшего**, не дальнего флангового.
- Ошибка: бьёт дальнего, пока ближний не тронут.
- Нейтрально: только один враг в контакте → 0.
- Тест: 2 врага (1 и 3 клетки), удар по 1-клеточному → +; по 3-клеточному → −.

**`retreat_low_hp`** (условный: реально безопаснее)
- Применимость: HP актёра < 30% max и есть куда отойти в безопаснее (вне `striking_distance`).
- Успех: отход в клетку, где число бьющих его врагов меньше, и (опц.) есть союзник/LOS-блок.
- Ошибка: при низком HP встал в ещё большую зону поражения.
- Нейтрально: безопаснее физически некуда; отход не снижает угрозу → 0.
- Тест: HP 20%, вышел из 2 контактов в 0 → +; полез в 3 контакта → −; ловушка → 0.

### 3.2 Отложены (нет данных/механики) — НЕ блокируют curriculum

- **`use_high_ground`** — высота не моделируется (§2). Вернёмся, если/когда движок даст elevation.
- **`no_stack` безусловный** — «разнести союзников всегда» контр-продуктивен у choke/стенки;
  включим только как **ситуативный** штраф (стоять впритык под достижимым AoE/обстрелом), когда
  научимся определять зону угрозы. Пока — вне расписания.
- **`charge_from_cover`** — требует памяти последовательности ходов (выход из укрытия → атака)
  и бинарного укрытия; реализуемо, но дороже. Переносим в подэтап после уверенного `cover_shoot`.
- **graded cover (½/¾)** — не существует в движке; не эмулируем эвристикой без явной отметки.

## 4. Принципы reward-shaping (условия 2.3)

1. **Оценка политики — с полностью выключенным tactical shaping.** В `team_eval`/matchup/
   финальном замерах `tactics.enabled=false`, reward = чистый `TeamReward`.
2. **Раздельный учёт по тактике:** для каждого тега храним `applicable`, `fired`, `violated`
   (уже есть несущий слой — `shaping_diagnostics.json`, расширить полями применимости).
3. **Нельзя бонус за формально-подходящее, но глупое действие.** Детектор обязан учитывать
   достижимость/безопасность/ценность (см. поля «Нейтрально»). Ложный позитив = баг детектора.
4. **Ограничение по абсолютной величине.** `|Σ shaping за бой| ≤ cap · |WIN|` (cap по умолчанию
   0.3), считается по модулю от суммарного вклада, а не по знаковой сумме.
5. **Затухание.** `λ(iter)=max(0,1−iter/total_iters)`; в конце этапа проверяем обучение на
   чистом reward (λ=0) — навык должен удержаться без подпорки.
6. **Каждый новый/изменённый вес — A/B против варианта без этой поправки.** Не «добавили и
   верим»; добавили → сравнили с выключенным тегом на тех же сидах/side-swap.
7. **Мало и маленько.** Старт: 1 тактика, веса ≤0.1. Не поднимать вес автоматически при
   неудаче — сначала причина (§8).
8. Shaping — отдельный аддитивный член к `env.shape_reward` (потенциальный Ng'99 к `phi`
   остаётся как есть), с гейтами train-only / arena-applicable / decay / cap.

## 5. Метрики: три раздельных вида (условие 2.1, 3.A–D)

Для каждого этапа замеряем и НЕ смешиваем:

**A. Освоение навыка (`follow_rate`).**
`follow_rate(tag) = fired / applicable` по состояниям, где `applicable` (не по всем боям).
Снимаем дважды: на фиксированном известном наборе состояний и на новых состояниях того же
типа (не было в train). Тактика, воспроизведённая только на знакомых аренах, = gate не пройден.

**B. Практический эффект (без shaping).** Через `team_eval.run_matchup(candidate=model,
opponent=<Random|Greedy|Battlecast>, swap_sides=True)` на тех же аренах/сидах:
`dmg_dealt`, `kills_avg` (=`foes_alive` start−end), `ours_survival`, распределение
`win/loss/draw/mutual/open`. Для раннего этапа навыка допустимо «эффект ещё не вырос» — это
повод смотреть условия применимости и взаимодействие тегов, а не поднимать reward.

**C. Регрессия.** Повторный замер ключевых `follow_rate` и боевого эффекта по всем ранее
сданным этапам. Допустимое падение фиксируется **до** прогона (§6). Новый чекпойнт не
принимается, если новая тактика выучена, а старая задача просела ниже допуска.

**D. Sankey-диагностика PPO (для «недотоптания»).** Из `history.json`: движется ли политика
(KL после update, изменение argmax-распределения действий), выполняются ли шаги (`n>0`),
нормализуются ли advantages (есть — §1.2), не доминирует ли `value_loss`, растёт ли val-исход
при большем объёме.

## 6. Протокол этапа (обязательные блоки A/B/C/D + стоимость)

Каждый этап описывается однотипно. Ниже — общие шаблоны; §7 заполняет их по этапам.

- **A. Минимальная задача:** арена(ы), состав, целевая тактика, конкретный проверяемый скилл.
- **B. Проверка усвоения:** фиксированный набор состояний + новые состояния того же типа;
  порог `follow_rate` задаём до прогона (default 0.60 известных / 0.50 новых).
- **C. Боевой эффект:** matchup vs {prev-best, Random, Greedy/Battlecast}; одинаковые арены и
  сиды; side-swap; shaping off. Первичная диагностика — малая выборка (≥12 боёв); для решения
  gate — увеличиваем, пока bootstrap-CI по win не станет уже порога (default ≥30 боёв).
- **D. Сохранение:** регресс-набор предыдущих этапов; допуск падения (default: win−≤5 п.п. и
  follow_rate−≤10 п.п. относительно принятого чекпойнта).
- **Стоимость и остановка:** `smoke-test` (проверка: датасет содержит применимые примеры,
  детектор срабатывает на синтетике, политика вообще двигается) → если smoke не прошёл,
  **полноценный прогон не запускаем**. Основной прогон: `iters` из §8-диагностики. PASS/FAIL
  по B/C/D. Допускается **≤2** прицельные диагностические попытки; после них FAIL → стоп и
  отчёт с причиной. Арены генерируем только под текущий+ближайший этап, не все заранее.

Процесс передачи модели между этапами (условие §4):
1) подготовить train + фиксированный validation; 2) проверить legal-действия и метки учителя;
3) снять baseline до обучения; 4) обучить на минимальной задаче (init из принятого чекпойнта
предыдущего этапа через `rl.warm=`); 5) проверить усвоение; 6) при необходимости — ограниченный
диагностический эксперимент (§8); 7) сравнить эффект без shaping; 8) сохранить best; 9) регресс
по прошлым задачам; 10) только после PASS — следующий этап. Retention старых навыков —
смешиванием прошлых арен в train-пул (уже поддерживается: явные `arenas`/`scenario_sources` +
`variants_per_src`); отдельного replay-буфера нет, не выдумываем. Не обучаем каждый этап с нуля.

## 7. Curriculum по этапам

Порядок фиксирован. Новый этап стартует с принятого чекпойнта предыдущего (`warm`).
Новых тактик — не более 3 на этап. Тактики из §3.2 не вводятся, пока не снят блок.

### Этап 1. Первая исполнимая: `no_idle` на открытых зеркальных дуэлях 1v1
- A: `duel`, `melee×2`, `wall_profile="open"`, structured (`random_start=False`). Один навык:
  не стоять при доступном ударе/сближении.
- Тактики: **только `no_idle`** (вес 0.05), штраф пустохода 0.05. Остальные `enabled=false`.
- B: фикс. состояния «удар доступен/недоступен» + новые дуэльные позиции; follow(`no_idle`) ≥0.90
  известных / ≥0.80 новых.
- C: matchup vs Random (side-swap). Критерий: model win > random win; **зеркало model-vs-model**
  win≈loss (нет преимущества стороны). Не требовать поражения при перевесе.
- D: регресс не нужен (первый). Допуски зафиксировать для будущих.
- Стоимость: smoke (все ли шаги легальны, меняется ли argmax за 1 итерацию) → 1 диагностический
  эксперимент §8 → прогон. Если follow<порога после 2 попыток — стоп+отчёт (см. §9).
- **Это этап, который агент начинает сразу.**

### Этап 2. Фокус и добивание в melee: `focus_wounded`, `kill_shot`
- A: дуэли и 2v2 melee на открытом поле; цель — бить добиваемого/раненого, а не полного.
- Тактики: +`focus_wounded`, +`kill_shot` (по 0.10). `no_idle` остаётся.
- B: follow(kill_shot) там, где есть добиваемая цель ≥0.70; follow(focus_wounded) ≥0.60.
- C: `kills_avg` растёт против Random (был ~0 в swarm/spear — проверяем сдвиг); win matchup↑.
- D: `no_idle` не просел (допуск §6-D).

### Этап 3. Разные классы и дистанционная тактика: `kite_max_range`, `avoid_reach`, `priority_soft`
- A: 1v1 зеркальные по классу (melee/fast/reach/ranged/mobile_archer/tank), затем парные матчапы.
- Тактики: +`kite_max_range`, +`avoid_reach` (переопределённый), +`priority_soft`.
- B: follow(kite) у ranged vs melee ≥0.60 (на новых позициях); follow(avoid_reach) у melee vs
  reach-угрозы ≥0.55.
- C: ranged-vs-melee matchup win↑ против Random; урон, полученный от reach-угроз, ↓.
- D: focus/kill_shot не просели.
- Замечание: на этом этапе проверяем, что ranged НЕ получает бонус за сближение (штраф по
  переопределённому `kite_max_range`/`avoid_reach`), как требовалось в изначальной идее.

### Этап 4. Неравные матчапы и асимметрия
- A: асимметричные пары (ranged×melee, reach×fast, tank×melee), `team_sizes` ±1.
- Тактики: без новых; калибровка взаимодействия `priority_soft`↔`focus_wounded`.
- B/C: модель играет от роли (за танка — размен, за лучника — кайт). matchup↑ против Random.
- D: регресс по 1–3 (допуски §6-D).

### Этап 5. Укрытия, стены, вариативный старт: `cover_shoot`, `hold_choke`
- A: `wall_profile∈{scatter,pillars,corridor}` + `random_start=True`; choke/diagonal.
- Тактики: +`cover_shoot` (бинарный LOS), +`hold_choke`.
- B: follow(cover_shoot) там, где есть sight-стены ≥0.60; на новых позициях ≥0.50.
- C: выживаемость ranged под обстрелом↑; win на cover/choke аренах↑.
- D: 1–4 не просели. `hold_choke` детектор — по choke-клетке (проходимость из walls/pathfinding);
  если надёжное определение choke нет — тег отложить точечно, `cover_shoot` продолжить.

### Этап 6. Командная игра 2v2, концентрация: `focus_fire`, `anti_pincer`, `break_ring`
- A: 2v2 смешанные; pincer/ring архетипы; structured для честного A/B.
- Тактики: +`focus_fire` (команда/раунд), +`anti_pincer`, +`break_ring`.
- B: follow(focus_fire) ≥0.60; среднее число добитых врагов за бой ≥1.5 (цель — победить
  «россыпь»,diag §0 в swarm было 0).
- C: matchup 2v2 win↑ против Random и против Greedy; живых вражеских атакующих на закрытии↓.
- D: 1–5 не просели.

### Этап 7. 3v3 и сложнее геометрия + `retreat_low_hp`
- A: `n_side=3`, rich geometry; +situational отход.
- Тактики: +`retreat_low_hp` (условный).
- B: follow(break_ring/anti_pincer) держим ≥0.55 на 3+ целях; retreat срабатывает при HP<30%.
- C/D: как выше; на «тупых» открытых 3v3 равного состава — отсутствие преимущества стороны
  (mirror win≈loss), а не искусственный паритет против Random.

### Этап 8. Большие бои (4v4…6v6, swarm, boss_adds)
- A: `MAX_TEAM=6`; swarm (много слабых)+boss_adds; приоритет добивания слабых раньше танка.
- Тактики: усиление `priority_soft` (adds→boss) и `focus_fire`; новых не заводим.
- B: follow(priority_soft в swarm)↑; avg_kills в swarm ≥1 (раньше 0).
- C/D: полный регресс-набор; matchup на сложных↑ против Random.

### Этап 9. Полный микс и финальная независимая оценка
- A: все архетипы/размеры, `random_start`; обучение не на holdout.
- Тактики: весь включённый набор; `λ→0` на финальных замерах (проверка удержания без подпорки).
- B/C/D + приёмка §0. Финальная оценка — на **зарезервированном** holdout (§8.6), shaping off,
  side-swap, bootstrap-CI: тактические арены — уверенный люфт над Random; тупые зеркальные —
  отсутствие преимущества стороны.

> Этапов ровно 8 обучающих (1–8) + финальная приёмка (9). Порядок тактик можно менять,
> слишком сложный этап — делить на подэтапы, но не добавлять новые крупные этапы без нужды.

## 8. Диагностика PPO и инфраструктурные условия

### 8.1 Однофакторный эксперимент (перед этапом 1, не «автоматом» поднимать гиперпараметры)
Последовательно, один фактор за раз (не десятки комбинаций):
1. **Двигается ли политика:** после 1 update — KL≠0, argmax-распределение действий изменилось
   хотя бы в части состояний. Если нет — причина в `lr`/advantage/pipeline, копать сюда.
2. **Выполняются ли шаги:** `report.n>0`; число update-минибатчей = `iters·rollout·epochs/minibatch`.
   Прогоны `us_ppo_*` шли с override `iters=8, rollout=64` при крошечном объёме обучения.
   `RlConfig` — `iters=60, rollout_steps=256`; стартовать с дефолта, не с overrides.
3. **Нормализация advantages:** есть (`rollout.normalize`) — проверить, что не перетирается.
4. **value_loss не доминирует:** если `vf_coef·value_loss ≫ policy_loss`, критик глушит политика —
   снизить `vf_coef` или чаще обновлять критику.
5. **Объём → качество:** больше rollout/iters улучшает val-исход. Если нет — проблема в данных/
   задаче, а не в гиперпараметрах.
После — зафиксировать рабочие `lr/iters/rollout/minibatch/target_kl` для этапа и НЕ крутить их
без новой гипотезы. **Если PPO не берёт простую дуэль — curriculum на PPO не разворачиваем.**

### 8.2 Реально блокирующие технические проблемы (подтверждено кодом)
- **RandomPolicy-соперник:** в matchup есть `ModelController`/`TeacherController` (greedy/
  battlecast), отдельного `RandomController` (uniform по legal) **нет**. Для baseline-сравнений
  нужен маленький контроллер, отдающий легальный случайный индекс через `obs["legal"]`. Блокирует
  §C на всех этапах. (Не «архитектура» — тонкий контроллер поверх существующего интерфейса.)
- **Поля применимости в diagnostics:** `shaping_diagnostics.json` пишет phi/reward/value, но не
  `applicable/fired/violated` по тегам. Без этого `follow_rate` неизмерим. Блокирует §B.
- **`hold_choke` детектор choke-клетки** требует надёжного определения прохода (walls/pathfinding);
  пока не реализовано — точечно отложить тег (не блокирует другие этапы).
- **Точность героя** в `apply_actor` — глобальный `t.hit_chance` (помечено «долг»). Для
  `kill_shot`/`focus_wounded` использовать ту же формулу ожидаемого урона, что среда, иначе
  детектор расходится с фактом. Ограничение, не блокер.

### 8.3 Что можно отложить без блокировки
- `use_high_ground` (нет elevation), graded cover (нет в движке), `charge_from_cover`
  (последовательность ходов), безусловный `no_stack`.
- Анти-забывание через отдельный replay-буфер (пока хватает смешения прошлых арен в train-пул).
- Архитектурные правки сети/action-space/симулятора — только если §8.1 показал конкретную
  причину неусвоения навыка. Фокус плана — обучение/данные/reward/покрытие, не рефакторинг.

### 8.4 Holdout, train/validation
- Три пула: train — обучение; validation — отбор чекпойнта и ограниченная диагностика;
  holdout — финал после настройки. `rl.py` уже режет grouped-by-name (train/val/holdout) и не
  обучается на holdout; split по сценариям (имя арены = группа), не по почти одинаковым состояниям.
- `ho_*`/`ho2_*` **уже участвовали** в слепой настройке весов → называть их «нетронутым финальным
  holdout» нельзя. Для честной финальной приёмки зарезервировать новый набор (другой seed,
  `holdout.py`) либо явно оговорить их статус. Ранние этапы можно вести на корректном
  train/validation по сценариям, не блокируясь идеальным holdout.
